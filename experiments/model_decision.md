# Phase 5C model decision — release `anomaly-stack-v1`

Status: **frozen**. This document records the Phase 5B selection decision and the
Phase 5C release that makes it reproducible, auditable, and safe to run in the
real ingestion path. It does not reopen, retune, or re-evaluate the decision.
`experiments/protocol.md` and `experiments/phase5b_protocol.md` remain the
preparation/comparison records this inherits from.

The machine-readable twin of this document is
[`experiments/releases/anomaly-stack-v1.json`](releases/anomaly-stack-v1.json),
generated by `scripts/create_release_manifest.py` — read that file for exact
values; this file explains what they mean and why they were chosen.

## Selected configuration

```text
Release ID:      anomaly-stack-v1
Layers:           A_global + D_burst
Fusion method:    stouffer (equal weight, two layers)
Review budget:    1% of a snapshot's transactions
Mode:             unsupervised only
Training seed:    42 (IsolationForest / MiniBatchKMeans inside layer A)
```

- `A_global` — transaction-structure anomaly scoring (Isolation Forest + ECOD,
  scored globally rather than within a KMeans shape family — the ablation found
  the global variant wins here because the target *is* a shape family, so a
  stratified score would treat the family's own members as its majority and stop
  flagging them).
- `D_burst` — population-level CoinJoin/peeling burst detection (Poisson EWMA
  control chart + Bayesian online change-point posterior over the motif count
  series).
- `S_supervised` exists in the codebase as a research comparator only. It trains
  on the fixture's generator-truth labels, which are close to the deterministic
  rule's own predicate — legitimate for bounding headroom, not for production.
  It becomes eligible for production only after real analyst review decisions
  exist (`app.ml.findings.review_decision_labels`, which returns `None` until at
  least 50 decisions with at least 10 positives exist, so the switch cannot
  silently flip itself on).

## No static model artifact — this is the point, not a gap

`A_global` and `D_burst` are **dynamically refit** on each snapshot's own
earliest 70% of transactions (`reference_fraction=0.7`) every time
`materialize_ml_findings` runs. There is no `.joblib`, no pickled estimator, no
file to version or to go stale relative to a schema change.

That means the usual release question — "which artifact is loaded" — has no
answer here, and pretending otherwise (shipping a fake static file, or a version
string with nothing behind it) would be worse than having no release record at
all. What *can* be versioned, and what this release freezes, is the **procedure**:

- which layers run and how they fuse (`app.ml.findings.release_identity()`);
- the training seed those layers use;
- the transaction feature contract layer A scores on (`app.ml.grains.TRANSACTION_COLUMNS`,
  hashed into `feature_columns_sha256`); layer D derives its motif count series
  from the same table's family flags and adds no columns of its own;
- the default review budget.

`release_identity()` returns exactly those fields. `release_manifest_sha256()`
hashes them. **Both are computed from code, not read from a file at runtime** —
`app/ml/findings.py` never depends on `experiments/` existing in a deployed
environment. The JSON manifest in this directory is generated *from* those
functions for human review; it is documentation of the code, not a second source
of truth the code reads back.

`model_run_id(snapshot_id, budget)` combines the release's identity hash with a
specific snapshot and budget into one deterministic ID. Re-scoring the same
snapshot under an unchanged release always reproduces the same ID — a reviewer
(or a test) can recompute it independently rather than trusting a value stamped
at write time. It changes automatically the moment any field in
`release_identity()` changes, which is what makes it a safe substitute for a
versioned artifact hash when no artifact exists.

**Every stored ML finding carries `release_id`, `model_run_id`, and
`release_manifest_sha256`** in both its `coverage` and `feature_vector` JSON, and
the `finding.updated` case event carries the same. A reviewer opening any single
finding can always answer "which scoring release, and which specific run,
produced this."

### Git commit SHA capture strategy

`scripts/create_release_manifest.py::_git_commit()` shells out to
`git rev-parse HEAD` (commit), `git rev-parse --abbrev-ref HEAD` (branch), and
`git status --porcelain` (dirty-tree flag) at manifest-generation time, rather
than trusting a manually-typed SHA. If git is unavailable (e.g. a tarball without
`.git`), the manifest records `commit: null` with the underlying error rather
than fabricating a value. A manifest generated from a dirty tree is still
written — `dirty: true` is itself audit-relevant information, not a reason to
fail — but a release intended for deployment should be re-cut from a clean,
committed tree so `dirty: false` and the commit SHA are trustworthy together.

## Known limitations (also machine-readable in the release JSON)

- **Synthetic-fixture evaluation only.** No number here is a claim about
  real-world detection accuracy.
- **No ownership, origin, criminality, or IP-to-wallet attribution claim** is
  made anywhere in this stack, at any layer, in any stored finding. IP, GeoIP,
  ASN, and relay-observation fields are used only as bounded k≤2 graph-context
  features (endpoint/ASN co-occurrence within a trailing window) — never as
  evidence of wallet ownership.
- **Unsupervised scoring cannot reliably separate a structurally identical
  benign payroll run from a real CoinJoin.** The discrimination task measures
  exactly this, and the deterministic rule remains the best available comparator
  on it. Analyst-labelled reviews are required before a supervised model may
  score production cases; until they exist in sufficient volume,
  `review_decision_labels` returns `None` and no supervised layer runs.

## Fallback behaviour

Every outcome below is a distinct, visible `ml_status` on the `import.completed`
case event. None of them can fail an ingestion that has already committed correct
evidence and correct deterministic (Phase 4) findings:

| Condition | `ml_status` | Ingestion / deterministic findings |
| --- | --- | --- |
| `TRACEX_ML_FINDINGS=0` | `disabled` | unaffected |
| Optional `ml` extra not installed | `unavailable` | unaffected |
| Scoring raises any exception | `error:<ExceptionType>` | unaffected |
| `TRACEX_ML_REVIEW_BUDGET` outside the safe range `(0, 0.5]` | `invalid_budget` | unaffected |
| `TRACEX_ML_REVIEW_BUDGET` not a number at all | falls back to the default `0.01` with a logged warning at `Settings` construction (never crashes app startup) | unaffected |
| Successful score, nothing clears the budget | `no_rows_flagged` | unaffected |
| Successful score | `written`, `ml_finding_count>0`, `ml_model_run_id` set | unaffected |
| Re-running the same completed snapshot (worker restart, retry) | idempotent no-op; existing findings are not duplicated | unaffected |

Architecture: `upload → worker ingestion → committed snapshot → graph →
deterministic findings → ML triage findings → existing findings API → frontend`.
The ML stage runs strictly after the deterministic findings, inside the same
background worker job that already builds the graph — never inside the upload
request handler and never inside a graph-query request path.
