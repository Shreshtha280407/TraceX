# Phase 5B protocol — offline model comparison and selection

Status: comparison and selection only. Nothing in this phase touches the production API, the findings endpoint, the frontend, the Docker image, or the offline LLM — that is later, separately authorized work. Phase 5A did not train a model; this document does not rewrite that history. `experiments/protocol.md` remains the Phase 5A preparation record; this file is the Phase 5B experiment record that inherits its fixed identity (`TRAINING_SEED=42`, `TRAINING_BUDGET=600s CPU wall-clock per candidate fit`) rather than redeclaring it.

## Reproducibility identity

- Fixture: `datasets/phase5a_100k/`, generated by `python3 fixtures/phase5a_100k/generate.py --output datasets/phase5a_100k --formats csv,ndjson --verify` (generator/config hashes recorded in `fixture_manifest.json`, reproduced there — not restated here since it drifts on every regeneration).
- Training seed: `42`, fixed, used for every candidate fit and every stability rerun.
- Training budget: `600` seconds CPU wall-clock per candidate fit. A candidate that cannot fit within this budget on the reference snapshot is recorded ineligible, not granted more time.
- Threads: `TRACEX_ML_THREADS` env var, default `min(4, os.cpu_count() or 1)` — a safe bound, not "use every core." Applied to `OMP_NUM_THREADS`/`OPENBLAS_NUM_THREADS` before numpy/sklearn import and passed as `n_jobs=` to both estimators.
- Memory: peak RSS measured via `resource.getrusage(RUSAGE_SELF).ru_maxrss` (POSIX stdlib, no new dependency), normalized to MB. The warning threshold is configurable per runner via `TRACEX_ML_RSS_WARNING_MB`; default `24576` (24GB) for Aditya's 32GB MacBook, leaving ~8GB free for macOS itself. A run exceeding the threshold is flagged in its report, not aborted.
- Hardware: CPU-only. No CUDA, no GPU, no Docker, no cloud/online model server, no Claude Code/Codex dependency at run time. The selected artifact must remain loadable on a 16GB Linux/Arch laptop — recorded python/scikit-learn/numpy versions in the artifact manifest are what a receiving machine checks compatibility against (see `scripts/phase5b_validate_artifact.py`).

## Frozen feature population

**Window size:** filtered to `WINDOW_SECONDS[0]` = 900 seconds (15 minutes) only — the exact window the deterministic engine's own `peeling_chain_candidate`/`coinjoin_like_structure` key-resolution uses (`app/engine/findings/deterministic.py::materialize_findings`), which is what makes a *real* join to `evaluation_truth.json`'s transaction-scoped labels possible (see below) rather than an invented one. Mixing 15m/1h/24h rows in one population would also conflate incomparable scales for a distance-based method like LOF.

**Feature columns:** exactly the 37 columns documented in `experiments/feature_package/README.md`, in the fixed order recorded there and re-derived at run time into `feature_manifest.json`'s `feature_columns` + `feature_columns_sha256`. Any run whose flattened columns don't match that frozen list and order fails loudly instead of proceeding.

**Source of features:** the real TraceX exporter only — `GET /v1/cases/{case_id}/features/export`, reached in-process via the same direct-pipeline pattern `scripts/phase2_100k_smoke.py` already uses at 100K scale (no HTTP layer, no synthetic feature table fabricated anywhere in this phase).

**Hard exclusions** (never enter the model input; enforced by a denylist test, not just by omission from the "include" list): every raw wallet/address/script value, all TXIDs, all case/source/evidence identifiers and locators, `entity_ref` itself, scenario names, split/group IDs, outcomes, reviewer decisions, synthetic seed identities/reasons, and the four Phase 4.1 risk-propagation fields (`risk_propagation_score`, `risk_seed_distance`, `risk_path_evidence_count`, `risk_seed_count` — metadata only, never model input, per `docs/phase5a_handoff.md`'s hard exclusion rule). No raw IP, endpoint, GeoIP country/ASN, or network-observation field exists anywhere in the exporter's current output — there is nothing of that kind to strip, and the leakage test asserts that absence rather than assuming it. `evaluation_truth.json` is never ingested and never becomes a feature; it is read directly off disk by the preparation script only to compute evaluation-only labels, kept in a column that never reaches `fit()`.

## Split policy

`evaluation_truth.json`'s `split_groups` assign transaction-index ranges (`g-001`–`g-007` = train_reference/70K, `g-008`–`g-009` = validation/15K, `g-010`–`g-012` = final_holdout/15K, untouched) to the three splits, time-contiguous and group-disjoint by construction. The preparation script reads the real timestamps at the two boundary indices directly from `datasets/phase5a_100k/transactions.ndjson` (generation-ordered) and classifies every feature row by comparing its real `window_start` against those two boundary timestamps — never by re-deriving indices from the exported rows themselves. Boundary ordering is asserted at run time; a violation fails the run rather than silently proceeding.

## Preprocessing

Missing-value imputation uses fixed constants per column (documented in `feature_package/README.md`) — not fit from data, so leakage isn't possible there. The one thing that is fit is a single `sklearn.preprocessing.StandardScaler`, fit on `train_reference` rows only (after imputation) and applied unchanged to validation and final holdout. No other encoding or transformation is used.

## Candidates

| Candidate | Eligibility | Notes |
| --- | --- | --- |
| Phase 4 deterministic rule-only baseline | Always | Not an ML model. A row's score is 1 if a real `FindingRecord` exists at that exact `(entity_ref, window_start, window_end)` key (ties broken by real `rank` ascending), else tied-last. Pulled from the real findings API, not recomputed. |
| Isolation Forest | Unlabelled/limited-label numeric data | `random_state=42`, `n_jobs` per `TRACEX_ML_THREADS`. Fit on train_reference only. |
| Local Outlier Factor (novelty mode) | Same | `novelty=True`, `n_jobs` per `TRACEX_ML_THREADS`. Fit on train_reference only, scores unseen data only (never re-fit on validation/holdout). |

`HistGradientBoostingClassifier` is **not** run in this phase. The fixture's labels (`expected_peeling_chain_transaction_ids`: 3 rows; `expected_coinjoin_like_transaction_ids`: 35 rows, out of ~tens of thousands of windows) are synthetic engineering truth generated by the same rule logic being compared, not trustworthy real-world labels — supervised training on them would be circular. This is a predeclared decision, not a silent substitution.

## Evaluation-label join

Positive labels for Precision@K / benign-FP-rate are resolved by calling the real, already-tested `detect_peeling_chains`/`detect_coinjoin_like_transactions` (`app/engine/motifs/deterministic.py`) against the same ingested facts, then mirroring `materialize_findings`'s own key-resolution to find which `(address, 900s-window)` row each labeled txid maps to — the same resolution the production code itself performs, not a parallel invented heuristic. A labeled txid whose resolved key doesn't land in the prepared population (possible at split boundaries) is dropped from the positive set and the drop count is recorded. If, for a given metric, the usable positive set is empty, that metric is reported `"unavailable"` with a reason — never fabricated from `evaluation_truth.json` directly, never silently zero.

## Reporting

Every candidate's record includes: name/version/parameters, dataset/fixture/schema/preprocessing hashes, row counts by split, fit time, scoring time and batch-inference p95 latency, peak RSS, score direction, rerun rank-stability (Spearman correlation across two identical-seed reruns), review workload at the fixed budget, Precision@20/@50 and benign-FP/1,000 windows where the join is usable (else `"unavailable"` + reason), and an explicit limitations line: **synthetic-fixture evaluation only — does not prove real-world detection accuracy.**

## Selection rule (predeclared before any candidate runs)

Evaluate on validation only for comparison/selection; evaluate the final holdout exactly once, after the rule and all settings are frozen, with no further tuning from holdout results.

Select the simplest eligible candidate that:
1. completed its fit within the 600s budget;
2. stayed under the RSS warning threshold (`TRACEX_ML_RSS_WARNING_MB`, configurable per runner; 24GB default for Aditya's 32GB MacBook);
3. did not increase benign-FP/1,000 windows over the rule baseline by more than the predeclared margin (2×, or +5 per 1,000 windows, whichever is larger — a fixed rule stated here before any candidate is scored, not chosen after seeing results);
4. has the best validation Precision@20 among the candidates clearing 1–3, **if** the evaluation join produced a non-empty usable positive set for that metric.

`status` in the machine-readable result is one of three values, never conflated:

- **`"selected"`** — gates 1–3 passed and step 4's real, label-based Precision@20 comparison decided the winner.
- **`"selected_provisional"`** — gates 1–3 passed, but the join's usable positive set was empty (the realistic case at this label density), so selection instead used only stability, benign-FP rate, latency, and memory among the gated candidates. `real_world_accuracy` is recorded as `"unknown"` in this case, not merely unproven — and callers must treat `selected_provisional` as a materially weaker claim than `selected`, not the same outcome under a different label.
- **`"no_model_selected"`** — no candidate cleared gates 1–3; `selected_candidate` is `null`. Never a silent default to whichever candidate happened to run.

## Leakage checklist

- [ ] `evaluation_truth.json` is read only by the preparation script, off disk, never ingested through any API endpoint.
- [ ] No address, TXID, case/source ID, locator, scenario/group label, reviewer decision, or seed identity/reason appears in the frozen feature column list (enforced by `tests/unit/test_phase5b_no_leakage.py`).
- [ ] `risk_propagation_score`/`risk_seed_distance`/`risk_path_evidence_count`/`risk_seed_count` are excluded.
- [ ] The `StandardScaler` is fit on `train_reference` rows only.
- [ ] Split assignment is time-respecting and group-disjoint, derived from real transaction timestamps, not from the exported rows' own ordering.
- [ ] Any future candidate is compared only against the Phase 4 rule-only ranking, on identical records, snapshot, and review budget.
